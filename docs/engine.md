# 判定エンジンと出題エンジン

どちらも **参照実装は Python (`pipeline/`)** です。そこから TypeScript
(`app/vocab-core/`) へ移植し、差分テストで一致を担保しています。

## 判定 (`normalizer.py` / `normalizer.ts`)

解答はひらがなのみを受け付けます。表記ゆれを考えなくてよくなり、判定が
大幅に単純になるためです。同音異義語を取り違えて正解になるケースは理論上
ありますが（代表読みの衝突は約13%）、読みを正しく書けている時点で語彙は
理解できているので実害はありません。

判定は5段階で、結果は3値です。

| 段 | 条件 | 判定 |
|---|---|---|
| 1 | 正規化後の完全一致（`answers` のいずれか） | `correct` |
| 2 | 編集距離がしきい値以内（タイプミス許容） | `correct` |
| 3 | 部分一致（かな1文字は除く） | `unsure` |
| 4 | 準正解 `near` に一致、または編集距離内 | `unsure` |
| 5 | いずれにも該当しない | `wrong` |

正規化は NFKC → 括弧内の注記を削除 → 記号・空白を除去 → カタカナをひらがなへ
→ 先頭の助詞を削除 → 語尾（`すること` `ということ` など）を1回だけ削除、の順。

**`unsure` を用意することが、AI 判定を持たない構成の生命線です。**
判定の最終権限をユーザーに渡すことで「合っているのにバツ」を構造的に回避できます。
さらに、ここで集まる「ローカルは `wrong` と判定したがユーザーは正解と申告した」
ペアが、将来 AI 判定や訳語の改善を行う際の評価データになります。
**アプリ側でこのログを必ず蓄積してください。**

## 出題 (`scheduler.py` / `scheduler.ts`)

### FSRS（記憶モデル）

各語の**安定度**（忘れにくさ）と**難易度**を解答のたびに更新します。
FSRS-4.5 の既定パラメータを使用。評点は判定結果と自己申告から決まります。

| 判定 | 自己申告 | 評点 |
|---|---|---|
| `correct` (即答) | — | easy |
| `correct` | — | good |
| `unsure` | 正解だった | hard |
| `unsure` | 間違いだった | again |
| `wrong` | — | again |

### 出題間隔（アプリ側の使い方）

アプリは日付ではなく **解いた問題数** を時計に使い、語ごとに次に出す時点を
予約します。1日にまとめて解いても、間隔が保たれるようにするためです。

| 直前の結果 | 次に出るまで |
|---|---|
| まちがえた | 45問後 |
| あたった | 90問後 |

**設定では変えられません。** 短いほうが覚えた気にはなりますが、直前の記憶で
答えられてしまい身につきません。選ばせると短いほうを選んでしまうので、
学習効果の高い側に固定してあります。

予定を過ぎた語のうち、**最も長く待たせている語**から出します（同着なら抽選）。
3回連続で正解した語はクリア扱いになり、出題対象から外れます。

**予定が来た語が1つも無いときは、予定前の語を繰り上げず、初見の語で埋めます。**
繰り上げると「さっき出た語がまた出る」ことになり、間隔の決まりが崩れるためです。
その結果、学習を始めた直後は初見の語が続き、45問目あたりから復習が混ざり
始めます。抱える語は自然に増えていき、上限は94語（`WORKING_SET` =
GAP_CORRECT + 4）です。GAP_CORRECT より多く抱えていないと、予定より早く
一周してしまい、間隔の決まりのほうが破られます。

パートは100語なので、上限の94語はパートをほぼ抱えきる大きさです。
予定より短くなるのは、パート終盤で残りが数語になったときだけです。

### 重み付き抽選

**スコア順に並べて上から出すことはしません。** 並べてしまうと順番が固定され、
ユーザーは意味ではなく順番を覚えてしまいます。予定が同着の語のなかから
毎回抽選するので、同じ並びは二度と再現されません。

あわせて次の制御が入ります。

| 仕組み | 内容 |
|---|---|
| クールダウン | 直近に出た語は出さない（アプリでは16件。予定を守れないときの下限） |
| 干渉回避 | 直近6件と編集距離2以内、または読みが同じ語は出さない（`affect`/`effect` を隣接させない） |
| リーチ検出 | 8回以上間違えた語は重みを半減。出題過多による消耗を防ぐ |
| 新規投入 | 出す予定の語が無いときに投入（上限94語）。易しい順を保ちつつシードで揺らし、全ユーザーが同じ順序にならないようにする |

候補が尽きたときは段階的に条件を緩めますが、干渉判定は一気に捨てず
ウィンドウを狭めていき、「直前の語と紛らわしい」だけは最後まで守ります。

## 移植を一致させるための約束事

出題順は乱数と浮動小数の両方に依存するため、素朴に移植すると必ずずれます。
次の4点を全実装で守ってください。

1. **乱数は自前の SplitMix64** — 言語標準の乱数は実装が異なり再現しない
2. **抽選の重みは整数に量子化** — `exp`/`pow` の最終桁のずれで抽選結果が
   変わるのを防ぐ（`WEIGHT_SCALE = 1_000_000`）
3. **候補は必ず word_id 順に並べる** — Python の `dict` は挿入順を保つが
   他言語の辞書型は順序不定。並び順は抽選結果に直結する
4. **偶数丸めを使う** — Python の `round()` は偶数丸め。JavaScript の
   `Math.round()` は 0.5 を切り上げるので `roundHalfToEven` を使う

浮動小数の最大差は TypeScript で **1.705e-12** ありました（Swift では 0）。
重みを整数に量子化していなければ、この差が抽選の境界を跨いで出題順が
全崩れしていました。

## 差分テスト

```bash
cd pipeline && py test_normalizer.py && py test_scheduler.py
cd app/vocab-core && npm run verify
```

`npm run verify` は Python 実装の出力をベクタ化したもの
（`out/*_testcases.json`）と突き合わせます。「正解はどれか」を人が書かないので、
手書きテストより桁違いに広いカバレッジが得られます。

実測: **32,225 件が一致**（normalize 8,853 / variants 8,853 / judge 10,919 /
スケジューラ 3,600 ステップ）。

**`normalizer` か `scheduler` を触ったら必ず通してください。**
判定の不満（「これが不正解になるのはおかしい」）に出会ったら、
`test_normalizer.py` の `CASES` にケースを追加してから直します。
