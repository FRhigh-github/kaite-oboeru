# 英単語 — 書いて覚える

選択肢式ではなく**入力で答えさせる**英単語アプリ。出題順を毎回抽選するので、
「順番で覚えてしまう」ことが構造的に起きません。

**公開URL: https://frhigh-github.github.io/kaite-oboeru/**

iPhone の Safari で開き、共有ボタンから「ホーム画面に追加」でインストールできます。
オフラインで動作し、学習記録は端末内（IndexedDB）にのみ保存されます。

大学受験レベル 1,883 語の単語データをオープンデータから生成しています。
**外部 API を一切使わないため、データ生成コストも 0 です。**

## 設計の要点

### 解答はひらがなのみ

単語データは **表示用の表記** と **判定用の読み** を分離して持ちます。

```json
{
  "word": "objective",
  "meaning": "客観的",              // 画面に出す（漢字）
  "reading": "きゃっかんてき",       // 代表の読み
  "answers": ["きゃっかんてき", "もくてき", "ねらい", "もくひょう", ...],
  "pos": "adjective",
  "difficulty": 1,
  "tier": "part1"
}
```

ひらがな限定にすることで、漢字・送り仮名の表記ゆれを考えなくてよくなり、
判定が大幅に単純になります。同音異義語を取り違えて正解になるケースは
理論上ありますが（代表読みの衝突は約13%）、読みを正しく書けている時点で
語彙は理解できているので実害はありません。

### LLM を使わずに訳語を選別する

JMdict は語義ごとにタグを持っているので、機械的に選別できます。

| タグ | 意味 | 扱い |
|---|---|---|
| `arch` `obs` `dated` `rare` | 古語・廃語・稀用 | 捨てる |
| `sl` `vulg` `derog` | 俗語・卑語 | 捨てる |
| `organization` `work` `product` | 固有名詞 | 捨てる |
| `hon` `hum` `pol` | 敬語・謙譲語 | 捨てる |
| `yoji` `proverb` `id` | 四字熟語・ことわざ・慣用句 | 捨てる |
| `col` | 口語 | 代表訳にはしないが許容解には残す |
| `exp` | 慣用表現 | 他に候補が無い場合のみ使う |
| 分野タグ (`med` `comp` `law` …) | 専門用語 | 他に候補が無い場合のみ使う |
| **`uk`** | **通常かな書き** | **表示もかなにする** |

### 訳語のスコアリング

タグで絞ったあと、次の減点方式で代表訳を選びます（小さいほど良い）。

| 要素 | 減点 | 理由 |
|---|---|---|
| `sense_index × 3` | 0〜 | **最も効く**。その英語がその日本語の何番目の語義か |
| `gloss_pos` | 0〜 | sense 内で先頭に近いほど中心的 |
| 頻度バンド `nf` | 0〜4 | `nf01` ほど高頻度。`common` の真偽値より細かい |
| カタカナのみの表記 | +3 | 音写は意味を知らなくても答えられる |
| 接尾辞・助数詞 (`n-suf` `ctr`) | +3 | 「料」「版」は単独の語ではない |
| 前置詞を落として引いた | +2 | 確度が低い |
| 語形を変えて引いた | +1 | 確度が低い |

この2つがとくに重要でした。

- **`sense_index`** — `ignore` は `振り切る` の sense#3（4番目の語義）に
  直接ヒットします。sense 内の位置だけを見ていた頃は中心的な語義と誤認し、
  `ignore → 振り切る` という誤った訳語を選んでいました。
- **頻度バンド `nf`** — `橋`(bridge) と `陸橋` はどちらも sense#0 の常用語で
  区別がつきません。`nf` を使うと `橋` が正しく勝ちます。
  漢字1文字を減点するようなヒューリスティックでは `橋` を巻き添えにします。

### 前方展開

JMdict は名詞的な項目を動名詞で訳すことがあります。

```
無視 → "disregarding; ignoring"    ← "ignore" では引けない
予測 → "prediction; estimation"    ← "predict" では引けない
```

そのため `ignore → ignoring`、`predict → prediction` のように語形を
前方展開して引き直し、直接ヒットの結果と統合してからスコアで比較します。
直接ヒットがあっても統合するのが要点です（上の `ignore` の例のように、
直接ヒットのほうが質が低いことがあるため）。

### 品質の抜き取り確認

ルールベースである以上、機械的には測れない誤りが残ります。

```bash
py sample_quality.py --n 40          # ランダム抽出
py sample_quality.py --suspicious    # 怪しいものだけ
py sample_quality.py --word ignore predict
```

おかしい訳語は `data/manual_overrides.json` に書けば上書きできます。

`uk` の扱いが重要です。`然も` `以て` `且つ` は文語ではなく、
「かなで書くのが普通」なだけの日常語です。`uk` タグを見て
`しかも` `もって` `かつ` と表示します。

`dear` の候補にあった `州`（arch = 古語）のような誤りは、これで自動的に落ちます。

### 人手の逃げ道

ルールベースでカバーできるのは 98.4%（1,870/1,900）です。
残りは `data/needs_review.json` に自動で書き出されます。

```bash
# step4 が要対応リストを生成
cp data/needs_review.json data/manual_overrides.json
# answers を手で埋める
py step4_select.py   # 次回から反映される
```

訳語がおかしい語を見つけたときも、ここに書けば上書きできます。

## 実行

依存パッケージはありません（Python 3.10+ の標準ライブラリのみ）。

```bash
cd pipeline

py step1_fetch.py              # NGSL / NAWL / JMdict をダウンロード
py step2_build_wordlist.py     # 1900 語を選定しレベル分け
py step3_extract_glosses.py    # JMdict から訳語候補を逆引き
py step4_select.py             # タグで訳語を選別（LLM 不使用）
py step5_export.py             # アプリ同梱用データを書き出し
py step6_scheduler_vectors.py  # スケジューラの検証ベクタを生成
```

step1 と step3 は JMdict（展開後 63MB）を扱うため各 1〜2 分かかります。

## 設計上の判断

### なぜ SFI で単純にソートしないか

NGSL と NAWL の SFI は別コーパス由来で直接比較できません。NAWL の
`repertoire` は SFI 72.45 で NGSL の `red` (60.77) より高頻度に見えますが、
学術コーパス基準の頻度であり、実際には `repertoire` の方が明らかに難しい語です。
そのため各リスト内で順位を正規化し、NAWL に難易度の下駄
(`NAWL_DIFFICULTY_OFFSET`) を履かせています。

### 前置詞付き gloss の逆引き

JMdict の gloss は `to rely on` のように前置詞付きのことが多く、そのままでは
キーが `rely on` になって `rely` で引けません。前置詞を落としたキーでも
引けるようにし、優先度は直接ヒットより下げています（`phrasal` フラグ）。

### 難易度は頻度の近似

LLM を使わないため、`difficulty` (1〜5) は最終リスト内の頻度順の五分位です。
`shoe` や `wheat` のように「頻度は低いが簡単」な具体名詞は正しく評価できません。
FSRS の初期難易度として使う分には相対順序が保たれていれば十分ですが、
体感とずれる場合は `manual_overrides.json` で個別に補正してください。

### レベル感の調整

```bash
py step2_build_wordlist.py --cutoff 1400 --dry-run
```

`--cutoff` は「NGSL の何位までを中学レベルの基本語として捨てるか」です。
既定値 1400 は `dear / shoe / combination / blame / employer` 程度が
part1 の先頭に来るレベル感です。下げると易しく、上げると難しくなります。

## ロジック層 (`app/vocab-core`)

判定エンジンと出題エンジンは **UI に依存しない TypeScript パッケージ**として
切り出してあります。PWA でも React Native でもそのまま使えます。

Node 24 は TypeScript をそのまま実行できるので、ビルド構成は不要です。

### 検証

```bash
cd app/vocab-core
node src/verify.ts
```

Python 参照実装の出力をベクタ化して Swift と突き合わせる差分テストです
（normalize / variants / judge あわせて 24,000 件超）。
「正解はどれか」を人が書かないので、手書きテストより広くカバーできます。
**Swift 側の `Normalizer` を変更したら必ず通してください。**

### 移植は差分テストで担保する

参照実装は **Python (`pipeline/`)** です。そこから各言語へ移植し、
Python の出力をベクタ化したもの（`out/*_testcases.json`、約3.5MB）と
突き合わせて一致を確認します。「正解はどれか」を人が書かないので、
手書きテストより桁違いに広いカバレッジが得られます。

実測: **27,944 件が一致**（normalize 8,126 / variants 8,126 /
judge 8,092 / スケジューラ 3,600 ステップ）。

浮動小数の最大差は TypeScript で **1.251e-12** ありました
（Swift では 0）。`Math.exp` / `Math.pow` の最終桁が C の libm と
微妙に違うためです。抽選の重みを整数に量子化していなければ、
この差が抽選の境界を跨いで出題順が全崩れしていました。

### Windows で Swift を動かす際の注意（現在は未使用）

環境構築で踏んだ問題を記録しておきます。

| 症状 | 原因と対処 |
|---|---|
| `could not find CLI tool 'link'` | MSVC のリンカが必要。`swift-env.ps1` が Visual Studio の `vcvars64.bat` を読み込む |
| `unable to load standard library` | `SDKROOT` 未設定。`vcvars64.bat` が環境変数を組み替えるため、その後に設定し直す必要がある |
| `.ps1` が文字化けして構文エラー | PowerShell 5.1 は BOM 無し UTF-8 を ANSI として読む。**`.ps1` は UTF-8 BOM 付きで保存する** |
| `tools version 3.1.0 which is no longer supported` | 逆に **`Package.swift` は BOM を付けてはいけない**。BOM があると先頭の `// swift-tools-version:` が読めない |
| `swift test` が固まる | Windows のテスト検出の不具合（`all-discovered-tests.swift doesn't exist`）。`verify.ps1` を使う。XCTest は macOS 用に残してある |
| `unable to create symbolic link` の警告 | 無害。Windows でシンボリックリンクを作るには開発者モードが要るだけで、ビルドは成功している |

PowerShell 5.1 では native コマンドに `2>&1` を付けると stderr が
エラー扱いになり、終了コード 0 でも失敗と判定されます。
`swift build` は警告を stderr に出すので、リダイレクトせず
`$LASTEXITCODE` で判定してください。

## normalizer.py — アプリの心臓部

これは**参照実装**です。Swift 側で同じ挙動を実装し、
`out/normalization_testcases.json`（8,125 ケース）で一致を検証してください。
両者がずれると「合っているのにバツ」が発生し、離脱に直結します。

判定は 3 値です。

| 判定 | 条件 | 挙動 |
|---|---|---|
| `correct` | 正規化一致 / answers 一致 / 編集距離内 | 正解 |
| `unsure` | 部分一致（惜しい） | **ユーザーに自己申告させる** |
| `wrong` | いずれにも該当しない | 不正解 |

`unsure` を用意することが、AI 判定を持たない構成の生命線です。
判定の最終権限をユーザーに渡すことで「合っているのにバツ」を構造的に回避できます。
さらに、ここで集まる「ローカルは wrong と判定したがユーザーは正解と申告した」
ペアが、将来 AI 判定や訳語の改善を行う際の評価データになります。
**アプリ側でこのログを必ず蓄積してください。**

### 画面構成

タブは3つです。**パート選択は「学習」タブの中**にあります
（別タブに分けると、どちらを開けばよいか分かりにくいため）。

| 画面 | 内容 |
|---|---|
| 学習 | 上部にパート表示 →「切り替え」でパート選択 → 選ぶとそのまま学習に入る |
| 統計 | 今日の解答数・正答率・定着度分布・苦手な語・判定のずれ |
| 設定 | バックアップ、**出典表示**（ライセンス必須）、データ消去 |

学習画面は 英単語 → かなキーボードで入力 → 3値判定。
`unsure`（惜しい）のときは「合ってた？」でユーザーが自己申告します。

### ひらがな専用キーボード (`src/kana-keyboard.ts`)

**`<input>` 要素を一切使っていません。** OS の IME を経由しないので、
漢字やカタカナへの変換が構造的に起こりえません。
文字列はキーボードのクラスが完全に保持し、表示は div で行います。

iPhone 標準に近いフリック入力です。

```
あ  か  さ  ⌫
た  な  は  ん
ま  や  ら ┌────────┐
ー  わ  小゛゜│ こたえる │
           └────────┘
```

- キーを押している間、上下左右にどの文字があるかを十字で表示する
- 24px 以上動かした方向の文字が確定する。動かさなければ中央の文字
- `ん` と `ー` は頻出なので専用キーにしてある（`わ` からのフリックでも出せる）
- `小゛゜` キーは直前の文字を巡回させる
  （`か→が`、`は→ば→ぱ`、`つ→づ→っ`、`や→ゃ`）
- 「こたえる」は右列の縦長ボタン

### パート分割

頻度順の全1883語を100語ずつ19グループに分けてあります
（グループ1が最も易しい）。**一度に1パートだけ**を出題対象にします。

学習画面上部の「切り替え」からパートを選ぶと、そのまま学習に入ります。
パートを変えると、その語だけでスケジューラを組み直します
（`buildScheduler`）。出題も進捗もそのパートに閉じます。

## scheduler.py — 出題エンジン

2つの要素からなります。

### 1. FSRS（記憶モデル）

各語の**安定度**（忘れにくさ）と**難易度**を解答のたびに更新し、
「いつ忘れるか」を推定します。FSRS-4.5 の既定パラメータを使用。

評点は判定結果と自己申告から決まります。

| 判定 | 自己申告 | 評点 |
|---|---|---|
| `correct` (即答) | — | easy |
| `correct` | — | good |
| `unsure` | 正解だった | hard |
| `unsure` | 間違いだった | again |
| `wrong` | — | again |

### 2. 重み付き抽選（出題順）

**本アプリの中核要件**です。忘れかけの語ほど高確率で選ばれますが、
**スコア順に並べて上から出すことはしません**。並べてしまうと順番が固定され、
ユーザーは意味ではなく順番を覚えてしまいます。毎回抽選するので同じ並びは
二度と再現されません。実測で「同じ語の次に来る語」は平均 3.0 種類でした。

あわせて次の制御が入ります。

| 仕組み | 内容 |
|---|---|
| クールダウン | 直近 12 件に出た語は出さない |
| 干渉回避 | 直近 6 件と編集距離2以内、または読みが同じ語は出さない（`affect`/`effect` を隣接させない） |
| リーチ検出 | 8回以上間違えた語は重みを半減。出題過多による消耗を防ぐ |
| 新規投入 | 復習待ちが10件を下回ったら投入。1日20語まで。易しい順を保ちつつシードで揺らし、全ユーザーが同じ順序にならないようにする |

候補が尽きたときは段階的に条件を緩めますが、干渉判定は一気に捨てず
ウィンドウを狭めていき、「直前の語と紛らわしい」だけは最後まで守ります。

### Python と Swift を一致させるための約束事

出題順は乱数と浮動小数の両方に依存するため、素朴に移植すると必ずずれます。
次の4点を両実装で守っています。

1. **乱数は自前の SplitMix64** — 言語標準の乱数は実装が異なり再現しない
2. **抽選の重みは整数に量子化** — `exp`/`pow` の最終桁のずれで抽選結果が
   変わるのを防ぐ（`WEIGHT_SCALE = 1_000_000`）
3. **候補は必ず word_id 順に並べる** — Python の `dict` は挿入順を保つが
   Swift の `Dictionary` は順序不定。並び順は抽選結果に直結する
4. **偶数丸めを使う** — Python の `round()` は偶数丸め。Swift の既定
   `.rounded()` は四捨五入なので `.rounded(.toNearestOrEven)` を指定する
